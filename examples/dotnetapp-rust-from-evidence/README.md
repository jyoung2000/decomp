# dotnetapp → Rust, reconstructed from evidence through the MCP client path (managed code)

This directory records the managed-code (.NET) demonstration run on 2026-10-06 (Linux host, non-certifying for Windows).

**What happened**
1. The Python API (`demo_setup.py`) created a case for `fixtures/dotnetapp/original` (framework-dependent .NET 8 app: `dotnetapp.dll` + apphost `dotnetapp.exe`) with the frozen fixture oracle as baseline and AI policy **No AI**.
2. The pipeline ran (11 jobs, all `completed`): inventory → dependency graph → feature discovery (8 oracle features, 9 scenarios) → capture original → `recover_managed` (ilspycmd 9.1.0.7988, project mode: `NotesApp/{Program,Menus,AppState,StateCorruptException}.cs`, 0 error markers, type listing matches native metadata) → `analyze_module` on the apphost (rizin) → scaffold candidate r1 → build → compare (**0/9**, honest failure: scaffold exits 64 with empty stdout) → deliver. M-IMPL was left **blocked**: *"No AI route configured: translating recovered dotnet code into rust needs interpretation. Next: connect a model (Connections) and set AI policy to 'AI-assisted', or open the task packet ev_01a11120ef58545bd00bc4 in an external client (Claude Code / Codex / Gemini via the Rebuild Studio MCP) and call propose_candidate."*
3. An external client (this Claude Code session, acting as a model client over the real `rebuild-mcp` stdio server with `--toolset rebuild`) read `list_features`, `search_evidence`, `get_evidence` for the task packet `ev_01a11120ef58545bd00bc4`, assembly metadata `ev_01a11120cf897590de9fc8` and the managed-recovery report `ev_01a11120d3c6d2971e9bda` / ILSpy recovery report `ev_01a11120d3c5f658e43a09`, plus the recovered C# that the ILSpy backend wrote under `cases/<case>/recovered/mod_7690fbcbdf8e2d60e0a5/`. It then authored `src/main.rs` from that evidence only, hand-emulating the System.Text.Json behaviour the recovered code depends on (`WriteIndented` 2-space layout, PascalCase property order `Version/UserName/Theme/Notes`, `[]` for an empty list, default `JavaScriptEncoder` escaping such as `"`/`<`/`é`, trailing `"\n"`; strict parsing → *"state file is not valid JSON"*, `null` root or null members → *"state file has missing fields"*, exit 4), `StreamReader.ReadLine` semantics (`\n`/`\r`/`\r\n`, BOM skipped, `Trim()`), `int.TryParse` for delete, and the usage error (exit 2). The fixture's `src/` and `expected/` were never read by the client; original source stays outside the adapter inputs (DR-8).
4. `propose_candidate` → candidate r2 `cand_01a11124a9daabb70652b3` → `build_candidate` (cargo, no dependencies) → `compare_candidate` → the verifier recorded **9/9 scenarios passed** on the first attempt (exit codes, stdout/stderr normalised CRLF→LF, byte-exact state files; verification report `ev_01a11124dcd24c80db899c`). Feature ledger: 8 verified, full parity = YES. Candidate r2 is last known good.
5. Independent check outside the app: `fixtures/tools/scenario_runner.py check --fixture fixtures/dotnetapp --launcher <out/dist/dotnetapp>` → `9 passed, 0 failed`.
6. `POST /cases/{id}/deliver` published `source/ dist/ evidence/ reports/` + `manifest.json` (24 files, every shipped file hashed). Copies of the report, comparisons, the attempt-1 verification report and the manifest are in `evidence/`.

**One evidence gap the client had to bridge**: the ILSpy output of `Menus.RunMain/RunNotes/RunSettings` shows no `null` case in the menu `switch`, which taken literally would loop forever on end of input. The feature list (`dotnetapp.menu_eof`: *"stdin ends mid-menu: app saves and exits 0"*) settled it: the reconstruction treats EOF as "back" in a submenu and "quit" in the main menu (each EOF prompt echoes a newline, as `Prompt` does). The verifier accepted that on the first try; it is still an inference, not something the decompilation states.

**Caveats recorded in the report**: the baseline is the frozen fixture oracle; the comparison host is Linux (`host_certifies_windows=False`; the environment block also reports `wine=True` (a host-level flag; this managed case ran no Windows-native code and the candidate is a Linux ELF)). Running the original under the Linux `dotnet` runtime would likewise be non-certifying for the Windows build (`Environment.NewLine` and console encoding differ there). The Rust binary here is an ELF built on Linux — the Windows `.exe` build of the same source is a Windows release gate. The parity report's "AI usage: no AI calls were made" refers to the app's own model routes; the candidate was authored by an external client over MCP.
